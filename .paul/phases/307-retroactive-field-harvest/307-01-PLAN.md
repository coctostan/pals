<objective>

## Goal

Build the deterministic normalization layer for retroactive field harvest: an authoritative dialect/normalization contract, a fixture-tested read-only harvester, and a proving-ground self-harvest of this repo's own 319 SUMMARY files into a deployment-namespaced ledger plus an unparseable manifest.

## Purpose

Phase 306 fixed the row schema (`Phase | Module | Status | Finding? | Actioned?`) for forward-looking UNIFY appends but explicitly deferred retroactive harvest. Phase 308 needs harvested cross-deployment evidence to produce its framework-improvement proposal batch. Field reconnaissance found the roadmap's assumed three SUMMARY dialects are actually five-plus, with status vocabulary well outside the six-value enum, so the harvest must be a specified, reproducible, testable transformation rather than a one-off agent read of 535 files.

This plan owns specification + tooling + self-harvest. Plan 307-02 owns executing the harvest across the external field deployments (quark, hybrid-energy-reasoner) and the aggregate roll-up.

## Output

- `docs/PALS-FIELD-HARVEST-NORMALIZATION-CONTRACT.md` — authority for dialect grammar, status mapping, `unparseable-phase`, namespacing, and retroactive `Actioned?` semantics.
- `tools/harvest-module-ledger.sh` — read-only POSIX shell/awk harvester.
- `tests/fixtures/field-harvest/` — one fixture per dialect plus edge cases, with expected golden output.
- `tests/helpers/field_harvest.sh` — sourceable guardrail helper (callers own TAP output).
- `.paul/field-harvest/pals-MODULE-LEDGER.md` and `.paul/field-harvest/UNPARSEABLE.md` — self-harvest artifacts.
- Bounded validation sections in both suites.

  <name>Task 1: Author the field-harvest normalization contract</name>
  <files>docs/PALS-FIELD-HARVEST-NORMALIZATION-CONTRACT.md</files>
  <action>
    Create the authority document for retroactive normalization. It is subordinate to
    docs/PALS-MODULE-EFFICACY-LEDGER-CONTRACT.md — state that explicitly and state that
    the Phase 306 contract wins on any conflict.

    Required sections:

    1. Purpose and source authority. Harvested output is a derived aid; each source
       SUMMARY remains authoritative for its own evidence. Harvest never mutates a
       source repository and never writes lifecycle artifacts.

    2. Deployment namespacing. Phase cell format is `{deployment}/{NN}-{PP}`, falling
       back to `{deployment}/{NN}` when a SUMMARY carries no derivable plan id. This
       preserves the five-column schema while preventing collisions (pals Phase 127 vs
       quark Phase 127 are distinct units).

    3. Dialect grammar for A, B, C, D, E and exclusion class X, each with the cited
       real-world example from the plan's reconnaissance table. Specify the anchor
       pattern the harvester keys on for each dialect and the precedence order when a
       single SUMMARY matches more than one (E > A/B/D > C).

    4. Status mapping — total function over observed tokens:
       - PASS, pass -> PASS
       - PASS_WITH_CONCERNS, PASS_WITH_BASELINE, PASS_WITH_KNOWN_BASELINE,
         PASS_WITH_RETRY, PASS-no-block -> PASS_WITH_CONCERNS
       - WARN, "warning only" -> WARN
       - BLOCK -> BLOCK
       - SKIP, skip, skipped-no-symbols, NOT_APPLICABLE, n/a -> SKIP
       - NOTE, "captured in SUMMARY" -> NOTE
       - Combined alternates (`PASS/SKIP`, `SKIP/PASS`, `PASS/WARN`) resolve to the
         weaker claim under the total order SKIP < NOTE < PASS < PASS_WITH_CONCERNS <
         WARN < BLOCK, so harvest never overstates module efficacy.
       - Any token absent from this table is NOT coerced; it becomes an unparseable
         row with reason `unmapped-status`. State this no-silent-coercion rule plainly.

    5. Finding? derivation: an explicit in-source `Finding?:` token wins; otherwise
       yes for PASS_WITH_CONCERNS / WARN / BLOCK, no for PASS / SKIP / NOTE.

    6. Actioned? derivation (D4): an explicit in-source `Actioned?:` token wins;
       otherwise `no` when Finding? is yes and `n/a` when Finding? is no. Retroactive
       harvest MUST NOT infer `yes`. Cross-reference the Phase 306 Actioned Trace Rule
       and state that promoting a historical row to `yes` is a Phase 308 human-confirmed
       activity, never a parser output.

    7. `unparseable-phase` definition with reason codes:
       - `no-dispatch-evidence` — no Module Execution Reports section, no module table,
         no [dispatch] line
       - `no-phase-id` — phase number not derivable from path or frontmatter
       - `unknown-module` — module name not resolvable against the canonical registry
       - `unmapped-status` — status token outside the mapping table
       - `ambiguous-module-set` — combined row with a non-enumerable remainder such as
         "and other advisory modules"; named modules still emit rows, the remainder does not
       - `excluded-foreign-evidence` — nested non-owning evidence tree (class X); an
         exclusion, not a parse failure
       Every unparseable unit is recorded with deployment, path, reason, and detail.
       Never fabricate a ledger row to avoid a manifest entry.

    8. Output artifacts and posture: `.paul/field-harvest/{deployment}-MODULE-LEDGER.md`
       and `.paul/field-harvest/UNPARSEABLE.md` are warm, derived, regenerable, and
       excluded from hot-artifact byte budgets. `.paul/MODULE-LEDGER.md` remains the
       forward-looking UNIFY-owned artifact and is never written by harvest.

    9. Non-goals: no telemetry, no push-based collection, no writes into field
       deployments, no automatic pals.json mutation, no module demotion, no replacement
       of source SUMMARY authority.

    Avoid: restating the Phase 306 schema as if it were new here, and inventing dialects
    not present in the cited reconnaissance — the contract must stay source-backed.
  </action>
