# Review Finding-Class Escalation

## Evidence

Quark Phase 127 promoted persisted `effectiveLimits` from stored shape to runtime enforcement authority. Three successive REV merge-gate rounds found Important gaps in the same shape-trust class across different readers. Fixes 127-04 and 127-05 closed four call sites, while round 3 found further container-shape and TOCTOU gaps and routed class-wide centralization to Phase 128 (`127-01-SUMMARY.md:125-129,154,156,167`).

The source explicitly concludes that surgical advisory absorption was the wrong shape for this cross-cutting trust class and that PLAN-time scoping should name persisted-state type-trust boundaries (`127-01-SUMMARY.md:154,156`).

## Problem

A high-risk plan can fix each review finding correctly while still underscoping the finding class. Successive reviews then rediscover sibling readers, producing fix/re-review loops and leaving the architectural decision implicit until late in the merge gate.

## Proposed Change

For high-risk planning where successive reviews expose the same finding class across readers, require an explicit human choice:

1. **Class-wide scope:** inventory the trust boundary/readers and cover the class in the current or a new approved plan; or
2. **Recorded bounded deferral:** finish the approved surgical scope, name uncovered readers/class risks, and route a future phase with source evidence.

The decision belongs in the normal PLAN/APPLY/UNIFY lifecycle. Review evidence informs the choice but does not make it automatically.

## Non-Goals

- No automatic REV lifecycle hook.
- No silent broadening of an approved fix.
- No rule that every repeated review finding requires class-wide remediation.
- No automatic blocker, proposal approval, merge decision, or STATE write.
- No changes to quark's already-routed Phase 128 debt from this repository.

## Risks

- “Finding class” can be defined too broadly and create scope creep.
- Mandatory inventories can burden low-risk/local changes.
- Teams may use deferral language mechanically without identifying real readers.
- Review tools may disagree; human judgment remains necessary.

## Validation Shape

If approved for future implementation, use contract examples covering one local defect, repeated sibling-reader defects, a justified surgical fix with explicit deferral, and a class-wide plan. Validate that no hook auto-expands scope or blocks lifecycle progress without workflow-owned evidence and a human decision.

## Human Route

A framework maintainer should decide whether this becomes planning guidance, a template prompt, or no change. Any implementation requires a separate approved PLAN; REV remains on-demand unless humans explicitly decide otherwise through normal lifecycle work.
