# Validation-Suite Decomposition

## Evidence

PALS validation callers are the repository's largest and fastest-growing live shell files. The post-v2.70 assessment measured 2,733 Pi / 2,136 cross-harness lines and called decomposition a separate medium-value, moderate-risk option (`.paul/assessments/2026-06-03-post-v2-70-next-milestone.md:46-54,98`). The post-v2.71 assessment measured 2,812 / 2,249 and raised the option to medium-high value because every milestone adds guardrails (`.paul/assessments/2026-06-04-post-v2-71-next-milestone.md:42-53,88,109`).

Phase 306 recorded the Pi caller at 2,478 lines (`306-01-SUMMARY.md:133-135`). Phase 307 kept new parsing in `tests/helpers/field_harvest.sh` but still measured the Pi caller at 2,922 lines and retained the standing decomposition candidate (`307-01-SUMMARY.md:79-81,170-172,224`). At Phase 308 APPLY baseline, the callers are 2,937 and 2,324 lines.

## Problem

The two top-level suites mix orchestration, large marker inventories, installation setup, and domain-specific guardrails. Their command output and TAP counts are authoritative, so casual extraction risks hidden failures, reordered checks, count drift, and unclear ownership. Continued additive growth increases maintenance context and makes each future guardrail harder to review.

## Proposed Change

Open a future **contract-first** milestone that:

- inventories sections, TAP ownership, shared setup, cleanup, and helper boundaries;
- defines which caller retains each TAP line and expected count delta;
- extracts one bounded responsibility at a time behind sourceable success/failure helpers;
- keeps top-level command output, order, counters, and failure diagnostics authoritative;
- proves behavioral parity and avoids abstractions that merely move a god file.

Use existing `tests/helpers/tap.sh`, `artifact_consistency.sh`, `module_instruction_semantics.sh`, and `field_harvest.sh` patterns as evidence, not as automatic templates for every section.

## Non-Goals

- No decomposition implementation in Phase 308.
- No rewrite of existing Phase 307 checks.
- No hard-coded total TAP plan if callers continue to use dynamic counters.
- No hidden TAP output from helpers.
- No conventional framework, dependency, CI, or runtime architecture change.
- No weakening of command-output truth or GitHub Flow gates.

## Risks

- Extraction can change TAP ordering/counts while tests still appear green.
- Shared helpers can create cross-suite coupling or harness-specific leakage.
- Large helpers can reproduce the same maintenance problem under a new path.
- Setup/cleanup movement can create nondeterministic temp-file behavior.

## Validation Shape

A future approved plan should pin baseline outputs and line counts, extract one section per task, mutation-test failure paths, compare ordered TAP names/counts, run both full suites after each boundary, and require artifact consistency plus `git diff --check`. Callers should retain TAP emission; helpers should return success/failure and bounded diagnostics only.

## Human Route

A framework maintainer should decide whether to schedule a dedicated next milestone, defer with a measurable growth trigger, or reject. This proposal does not authorize decomposition in Phase 308.
